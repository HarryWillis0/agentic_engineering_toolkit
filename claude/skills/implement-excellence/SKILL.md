# Implement Excellence

Work through every open `software-excellence` issue — generated by `/code-audit` — one refactor at a time, until all have open PRs or are closed.

## Invocation

```
/implement-excellence
```

No arguments needed. The label `software-excellence` is the source of truth.

## Phase 1 — Survey

1. Run `gh issue list --label software-excellence --state open --json number,title` to get every open issue.
2. Run `gh pr list --state open` to see what is already in flight (look for branches or PR bodies referencing each issue number).
3. For each issue, determine its state:
   - **Done**: issue is closed, or a merged PR has `Closes #N` in its body.
   - **In PR**: an open PR references it.
   - **Ready**: open, with no PR — SE issues are always independent, so there are no blockers.
4. Print a one-line status table before writing any code.

## Phase 2 — Pick next issue

Select the lowest-numbered **Ready** issue.

If nothing is Ready:
- Everything is Done or In PR → declare the backlog clear, list the PRs, and stop.
- The user interrupted → stop cleanly, summarise what was done and what remains.

## Phase 3 — Branch

SE issues always branch from `dev`. There are no blocking dependencies to check.

```bash
git checkout dev && git pull && git checkout -b <issue-num>-<short-slug>
```

Slug: 2–4 lowercase words from the issue title, hyphen-separated (e.g. `62-propagate-odds-errors`).

Always pull `dev` before branching.

## Phase 4 — Understand the refactor

Read the full issue with `gh issue view <N>`. The body always contains:
- **Problem**: the violation and why it matters, with a code snippet
- **Fix**: what the change looks like
- **Acceptance criteria**: what done looks like

Read the cited file(s) at the cited line numbers before touching anything.

## Phase 5 — Implement (refactor, not feature)

The golden rule: **no observable behavior change**.

### Test strategy

SE issues are pure refactors. The existing test suite is the behavior proof — passing tests after the refactor is sufficient evidence that behavior is unchanged.

Write new tests only when:
- You extract and export a **new public unit** (function, class, or module that didn't exist before). Use the `/tdd` red-green loop for that unit.
- The refactor **changes a public API signature** — update existing test(s) to match the new signature, and confirm they were failing before the fix (red step).

Never manufacture tests to cover the mechanics of a rename or an extract-method.

### Execution

1. Explore the affected code — confirm the violation matches the issue description.
2. If a new exported unit needs tests, write a failing test first (`/tdd` red step).
3. Make the refactor.
4. Run `pnpm format` on the files you changed.
5. Run the affected package's test suite to confirm green.
6. Run `pnpm typecheck` across all packages.
7. Fix any failures before continuing.

## Phase 6 — No-new-violations check

Before committing, scan the changed code for any **new** clean code violations introduced by the refactor. Check each:

- **CQS**: does a function now both mutate state and return a value?
- **SRP**: does a refactored unit do more than one thing?
- **Deep nesting**: three or more levels?
- **Long parameter lists**: 4+ positional params?
- **Hidden side effects**: broad catch blocks swallowing errors?
- **DRY**: duplicated logic that could be a helper?
- **Naming**: names that describe how rather than why?

If you find a new violation you introduced, fix it inline before committing. Do not file it as a separate issue — you caused it, you own it.

## Phase 7 — ADR check

Before committing, ask: did this refactor reveal or impose a non-obvious architectural constraint? Write an ADR if any of these apply:

- A real alternative pattern was rejected and the reason isn't obvious from the code
- A constraint exists that could bite someone later (e.g. "this pattern breaks under horizontal scaling")
- The new structure was chosen for a non-obvious reason (not just "cleaner" — but why it must be this way)

**If yes:** write `docs/adr/NNNN-<slug>.md` (next sequential number). Follow the format in existing ADRs.

**If no:** pure renames, extractions, and reorderings do not need ADRs.

## Phase 8 — Commit and PR

Run `/commit` to stage, commit (with `Closes #N` in the body), and push the branch.

Then open a PR:

```bash
gh pr create --title "<commit subject>" --base dev --body "..."
```

PR body: one short paragraph describing the structural improvement and why it matters (intent, not mechanics), plus `Closes #N`. **No test plan section.**

## Phase 9 — Loop

Go back to **Phase 2** and pick the next Ready issue. Continue until the backlog is clear.

## Stopping conditions

- All SE issues are Done or In PR → declare the backlog clear and list the PRs.
- The user interrupts → stop cleanly, summarise what was done and what remains.

## Rules

- **One issue per branch.** Always branch from `dev`. Never mix two issues on one branch.
- **Always pull `dev`** before creating a new branch.
- **No behavior change.** If unsure, run the tests. Passing tests = safe.
- **No new violations.** Verify the changed code passes Phase 6 before committing.
- **Existing tests are the coverage.** Do not write tests to cover unchanged behavior.
- **New exported units get tests.** If you extract something new and public, drive it with `/tdd`.
- **Green before moving on.** Tests and typecheck must pass before the PR is opened.
- **Commit messages follow project conventions.** Use `/commit`, not a raw `git commit`. Type is always `refactor:` (or `fix:` for genuine bug fixes found during refactoring).
- **No speculative cleanup.** Only address what the current issue's acceptance criteria require. If you spot another violation, let `/code-audit` file it separately.
