# Implement Dependencies

Work through every open `dependencies` issue — generated by `/dep-audit` — one upgrade track at a time, until all have open PRs or are closed.

## Invocation

```
/dep-implement
```

No arguments needed. The label `dependencies` is the source of truth.

## Phase 1 — Survey

1. `gh issue list --label dependencies --state open --json number,title,body` to get every open issue.
2. `gh pr list --state open` to identify what is already in flight (match by `Closes #N` in PR bodies or branch names containing the issue number).
3. Classify each issue:
   - **Done**: closed, or a merged PR references it.
   - **In PR**: an open PR references it — skip, don't re-implement.
   - **Ready**: open, no PR in flight.
4. Print a one-line status table before writing any code.

## Phase 2 — Pick next issue

Select the lowest-numbered **Ready** issue. Dependency upgrade issues are always independent of each other — there are no blockers to check. Security issues (type `fix:`) take priority over `chore:` upgrades regardless of number.

If nothing is Ready:
- Everything Done or In PR → declare the backlog clear, list the PRs, and stop.
- User interrupted → stop cleanly, summarise what was done and what remains.

## Phase 3 — Branch

Dependency issues always branch from `dev`. Always pull first.

```bash
git checkout dev && git pull && git checkout -b <type>/<issue-num>-<short-slug>
```

- Type prefix: `fix/` for security patches, `chore/` for upgrades.
- Slug: 2–4 lowercase words from the issue title (e.g. `chore/76-eslint-v10`, `fix/75-security-patch`).

## Phase 4 — Read the issue

`gh issue view <N>` — read the full body. The issue always specifies:
- Which packages move and to which version
- Key breaking changes to handle
- Acceptance criteria

Do not start upgrading until you understand all the breaking changes listed.

## Phase 5 — Implement the upgrade

The approach varies by upgrade type. Read the issue to determine which applies.

### Security patches

```bash
pnpm update --filter <workspace> <pkg1> <pkg2>
```

For transitive vulnerabilities where the parent hasn't updated yet, add a `pnpm.overrides` entry in the root `package.json`:

```json
"pnpm": {
  "overrides": {
    "vulnerable-pkg": "^fixed-version"
  }
}
```

Re-run `pnpm audit` after updating — confirm the specific advisories from the issue are resolved.

### Major version upgrades (coupled ecosystem)

Use `pnpm add -D` to move all packages in the group together in one install:

```bash
pnpm add -D "pkg-a@^<major>" "pkg-b@^<major>" ... --filter .
```

After installing, check for config breakage:
- Read all relevant config files (e.g. `eslint.config.js`, `.prettierrc`, `tsconfig.json`) and verify the APIs used still exist in the new version.
- Cross-reference with the breaking changes listed in the issue.
- Fix any config changes required before running checks.

### Formatter upgrades

After updating a formatter (Prettier, its plugins), run:

```bash
pnpm format:check
```

If files fail, the new formatter has changed its output — this is expected. Apply the new formatting:

```bash
pnpm format
```

Spot-check the diff to confirm the changes are purely cosmetic (whitespace, line breaks, attribute wrapping). If you see logic changes, investigate before committing.

## Phase 6 — Verify

All of the following must pass before opening a PR:

```bash
pnpm format           # apply formatting to any files changed by the upgrade
pnpm audit            # security issues only — confirm resolved advisories are gone
pnpm typecheck        # across all packages
pnpm lint             # 0 errors (warnings are acceptable if pre-existing)
pnpm test             # run each workspace package's tests
```

If any check fails:
- Type errors: read the TS release notes for the relevant change; fix the usage rather than loosening config.
- Lint errors: update the ESLint config to match the new plugin's API — do not disable rules to make them go away.
- Test failures: investigate the root cause; a test failure after a dep upgrade means either a real breakage or a test that was coupling to an implementation detail.

Do not open a PR with a failing check.

## Phase 7 — Commit and PR

Use `/commit` to stage, commit (with `Closes #N` in the body), and push.

Then open a PR:

```bash
gh pr create --title "<commit subject>" --base dev --body "..."
```

PR body:
- One short paragraph on what moved and what it achieves (resolved CVEs, new major version features, etc.)
- `Closes #N`
- **No test plan section.**

## Phase 8 — Loop

Go back to **Phase 2** and pick the next Ready issue. Continue until the backlog is clear.

## Rules

- **One issue per branch.** Never mix two upgrade tracks on one branch.
- **Always pull `dev`** before branching.
- **Read breaking changes before touching packages.** The issue body lists them — don't skip this.
- **Security first.** If both a security patch and an upgrade are Ready, take the security patch first.
- **`pnpm audit` is the acceptance test for security issues.** A clean audit output is required — not just "fewer vulnerabilities".
- **Format changes are expected after formatter upgrades.** Apply and commit them in the same PR — do not file a separate formatting PR.
- **Do not loosen config to silence failures.** If a type error or lint error surfaces after an upgrade, fix the code or the config correctly — don't add `@ts-ignore` or disable rules.
- **Green before moving on.** All checks must pass before the PR is opened.
- **Commit messages follow project conventions.** Use `/commit`. Type is `fix:` for security patches, `chore:` for upgrades.
