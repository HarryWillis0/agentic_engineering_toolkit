# Implement Accessibility

Work through every open `accessibility` issue — generated by `/a11y-audit` — one fix at a time, until all have open PRs or are closed.

## Invocation

```
/implement-a11y
```

No arguments needed. The label `accessibility` is the source of truth.

## Phase 1 — Survey

1. Run `gh issue list --label accessibility --state open --json number,title` to get every open issue.
2. Run `gh pr list --state open` to see what is already in flight (look for branches or PR bodies referencing each issue number).
3. For each issue, determine its state:
   - **Done**: issue is closed, or a merged PR has `Closes #N` in its body.
   - **In PR**: an open PR references it.
   - **Ready**: open, with no PR.
4. Print a one-line status table before writing any code.

## Phase 2 — Pick next issue

Select the lowest-numbered **Ready** issue.

If nothing is Ready:
- Everything is Done or In PR → declare the backlog clear, list the PRs, and stop.
- The user interrupted → stop cleanly, summarise what was done and what remains.

## Phase 3 — Branch

Branch from `main`.

```bash
git checkout main && git pull && git checkout -b <issue-num>-a11y-<short-slug>
```

Slug: 2–4 lowercase words from the issue title, hyphen-separated (e.g. `14-a11y-image-alt-text`).

Always pull `main` before branching.

## Phase 4 — Understand the fix

Read the full issue with `gh issue view <N>`. The body always contains:
- **Frontend(s) affected**: which implementation(s) to touch
- **Problem**: what is broken and why it matters to users with disabilities, with a code snippet
- **Fix**: what the change looks like with a before/after snippet
- **Files to update**: exact file paths and line numbers
- **Acceptance criteria**: what done looks like

Read every cited file at the cited line numbers before touching anything.

## Phase 5 — Implement

The golden rule: **fix only what the accessibility issue describes — no speculative cleanup.**

### What a good a11y fix looks like

Accessibility fixes are typically small, targeted changes:
- Adding a missing `alt` attribute
- Replacing a `<div onClick>` with a `<button>`
- Wrapping a form control in a `<label>` or adding `aria-label`
- Adding `lang` to `<html>` or `<title>` to a page
- Correcting a heading hierarchy
- Adding `aria-label` to a landmark or icon button

Do not refactor surrounding code, rename things, or change visual behaviour. The fix must be surgical.

### Test strategy

- Run the existing test suite after each fix. Passing tests confirm you have not broken behaviour.
- Write a new test when:
  - The fix adds a new interactive element or component that has no existing test coverage.
  - The fix changes a component's public API (e.g. adds a required prop). Update the existing test to cover the new API.
- Do **not** write tests to verify that an `alt` attribute is present or that a `lang` attribute exists — that is the acceptance criteria in the issue, confirmed by reading the code.

### Execution

1. Read the cited files at the cited lines to confirm the violation matches the issue.
2. Make the targeted fix across all affected files listed in the issue.
3. Run the project's formatter (e.g. `npm run format` / `pnpm format`) on the files you changed.
4. Run the affected frontend's test suite and type-checker:
   - Svelte: `npm run check && npm test` (from `frontends/svelte/`)
   - React: `npm test` (from `frontends/react/`)
5. Fix any failures before continuing.

## Phase 6 — Verify no regressions

Before committing, confirm:

- **No new broken semantics**: you have not removed a valid landmark, heading, or existing `aria-*` attribute while adding the fix.
- **No keyboard regression**: any element you touched is still reachable and operable via keyboard.
- **No visual regression**: the fix does not change layout, spacing, or colour in a way not described in the issue.
- **Acceptance criteria met**: re-read the issue's acceptance criteria and tick each one mentally.

If you spot a separate accessibility problem while working, do **not** fix it inline. Note it and let `/a11y-audit` file it as its own issue.

## Phase 7 — Commit and PR

Run `/commit` to stage, commit (with `Closes #N` in the body), and push the branch.

Then open a PR:

```bash
gh pr create --title "<commit subject>" --base main --body "..."
```

PR body: one short paragraph describing which accessibility barrier is removed and what user experience improves as a result (intent for users, not implementation mechanics), plus `Closes #N`.

Include a short **Test plan** checklist:
- Manual steps to verify the fix (e.g. "navigate to /articles with a screen reader — image alt text is announced")
- Which automated checks pass (`npm test`, `npm run check`)

## Phase 8 — Loop

Go back to **Phase 2** and pick the next Ready issue. Continue until the backlog is clear.

## Stopping conditions

- All accessibility issues are Done or In PR → declare the backlog clear and list the PRs.
- The user interrupts → stop cleanly, summarise what was done and what remains.

## Rules

- **One issue per branch.** Always branch from `main`. Never mix two issues on one branch.
- **Always pull `main`** before creating a new branch.
- **Surgical fixes only.** Change the minimum required to satisfy the acceptance criteria.
- **No visual regressions.** Accessibility fixes must not alter the visual design.
- **Green before moving on.** Tests and type-checker must pass before the PR is opened.
- **Commit messages follow project conventions.** Use `/commit`. Type is always `fix:` — accessibility issues are genuine user-facing defects.
- **No speculative fixes.** If you notice another a11y problem while working, do not fix it inline — let `/a11y-audit` track it separately.
- **Cross-frontend issues get one branch.** If the issue lists both frontends, fix both in a single branch and PR. The branch slug uses `a11y` to make it obvious.
